# 立绘渲染性能分析（2026-10-30）

状态：**结论性文档**。记录了已落地的优化、实测数据、以及两条"跑通了但正确性
不成立/无收益"的路线（附失败原因），供后续接手直接续做，不必重走。

## 0. 一句话结论

单次立绘渲染在桌面约 **98 ms**、wasm 约 **200–300 ms**，代价来自**每次驱动变化
（眨眼/口型/物理弹簧）都从根遍历 546 个层节点、并为每个部件重算网格**——不是
常数因子问题。已验证可行的优化把总耗时压到约一半；要再降一个数量级，必须
做**子树级缓存**或**把变形搬到 GPU**，而子树缓存被 stencil（遮罩）语义卡住，
两条路都已在本文档给出结论与下一步。

## 1. 实测数据（基线，2026-10-30）

口径：桌面 headless，`--webpkg` 直连线上包，autoplay 180 s，同一段剧本。

| 指标 | 值 |
| --- | --- |
| 渲染次数 / 时长 | 306 次 / 44.0 s（该段 180 s） |
| 单次渲染 | **143.8 ms**（wasm 实测 293 ms，见 §1.1） |
| 其中 collect() | 118–123 ms |
| 其中 stage 侧（节点更新/规划） | 20–44 ms |
| 每次渲染访问层节点 | **546 个** |
| 每次渲染网格调用 | 397 次（命中率 ~50%） |
| 每次渲染产出可见部件 | **55 个** |
| 每层摊销成本 | **225 µs** |

关键比例：**546 个层节点里只有 55 个产出部件**（约 1/10），其余是容器层、
不可见部件、遮罩几何。遍历本身（选帧、Ctx 合成、字典构造、label 栈维护）
就是主要成本。

### 1.1 线上 wasm 实测（旧构建，公网站点）

`window.__animAudio` 探针，13 次渲染采样：

- 单次渲染 293 ms，collect 占 79%，`grid_calls` 6370（13 次渲染合计）
- 帧率在渲染瞬间跌到 10–15 fps（渲染 300 ms 内主线程全占）
- 单线程 wasm（`GODOT_THREADS_ENABLED=false`），没有后台线程可分担

### 1.2 各阶段耗时（分段剖面，180 s 段）

| 阶段 | 累计 | 占比 |
| --- | --- | --- |
| collect → travel | 23.0 s | 52% |
| 　└ 网格（`_grid_for`） | 12.7 s | 29% |
| 　└ 其余（选帧/Ctx/字典） | 10.3 s | 23% |
| stage 侧 | 3.6 s | 8% |
| 排序 + clip 解析 | 0.13 s | <1% |

## 2. 已落地的优化（commit `fae856a`，已验证）

四项，全部是**纯缓存/纯等价变换**，不改变任何输出：

1. **帧求值记忆化**（`_frame_for`）：key =（层节点, 动作时间 t），结果存在层
   节点上（上限 24 条 FIFO）。眨眼/口型只改变少数层的 t，其余层的帧求值
   直接命中。前提是 `_frame_content` 是 (frameList, t) 的纯函数——成立。
2. **warp / affine 记忆化**：挂在被记忆化的 frame dict 上（frame 对象身份稳定，
   所以缓存有效）。
3. **`chain_plan()` 仿射预合成**：把 warp 之间的纯仿射层预先合成，单点变换从
   O(链深) 降到 O(#warp)。等价性由 `player/tests/test_chain_compose.gd` 钉住：
   4000 条随机链（0–2 warp）与逐点循环对比，**最坏误差 0.0**。
   坑：Godot 标准构建的 `Vector2` 是 **32 位浮点**，中间量必须用裸 float 标量，
   否则 warp 输入被截断，误差 1e-5 量级。
4. **驱动重绘合并**：过渡中上限 0.15 s、静止/口型 0.45 s（原 0.30 s），
   单次渲染成本越高，合并间隔越宽。

效果（180 s 同段，事件流逐项一致 149 events / 148 say / effects 全同）：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 单次渲染 | 168 ms | **98 ms** |
| 渲染总耗时 | 53.0 s | **26.8 s** |
| collect | 47.9 s | 23.2 s |
| 网格 | 30.9 s | 12.7 s |

## 3. 已验证但**不可用**的路线（不要重复走）

### 3.1 Ctx 上下文复用（无 clip 上下文判定）

思路：层的输出只取决于（父 Ctx, 求值出的 frame, 物理偏移），三者用**对象身份**
比较即可判断"这一层没变"，命中时跳过矩阵乘、segs 数组拼接、网格键构建。

- 复用率 **79%**（`ctx_reuse 19273 / visits 24331`），单次渲染 148 ms → **无改善**。
  原因：省掉的只是 Ctx 构建，每层仍要选帧、查表、维护 label 栈、构建部件字典。
- 双路深比较（见 §4）抓到 **86/88 次 clip 不一致**：复用把"同一层在不同
  stencil 上下文下的 Ctx"混用了。
- 加 `clip_key`（stencil label 集合的稳定 hash）参与复用判定后：**0 处不一致**
  （正确），但复用率塌到接近 0（含遮罩的层占绝大多数），单次渲染 146 ms，
  **无收益**。改动已回退。

### 3.2 子树部件列表回放（最接近成功的一条）

思路：Ctx 复用时连同"该子树产出的部件列表"一起缓存；下次若该子树依赖的
**变量位图**与本次变化位图无交集，直接 `append_array` 回放，**连遍历都跳过**。

- 依赖位图用 62 位 int（变量名 → 位；按**值**比较，含 selector 派生变量），
  子树读集用 `|` 合并，判定 `(cur.dep_mask & _changed_mask) == 0`。
- 实测：单次渲染 **143 ms → 7.2 ms（20 倍）**，访问层数 546 → **13**。
- 但双路深比较抓到 **135/138 次 clip 不一致**（`part 1 clip 0 vs 1`，
  label = `トリミング枠` 裁剪框，`registry` 里该 label 为空）。
- 已尝试并排除的修法：
  1. 缓存子树的 **registry 贡献**（`reg_geoms`）并在回放时重放 `_register`
     —— 仍不一致；
  2. `_resolve_clips` 幂等化（回放的部件保留上次解析结果）—— 仍不一致；
  3. clip 自身排除从 `_gid` 改为对象身份 `is_same` —— 仍不一致；
  4. 加 `has_stencil` 子树标志（含遮罩的子树禁止回放）—— 仍不一致；
  5. 二分定位：**禁用 Ctx 复用后 0 处不一致**，所以问题在复用与 clip 的交互，
     不在回放本身。
- **未解的核心**：`part["clip"]` 的解析依赖"本轮 Inst 的 registry"，而 registry
  是遍历的副作用。回放跳过了遍历，就必须精确重放副作用；`_register` 只向
  **祖先 label** 注册，而 stencil 引用的是**同 Inst 内的任意 label**——两者
  不等价，这是目前没打通的地方。

## 4. 验证方法（可复用）

`ANIM_VERIFY=1` 环境变量开启（`EmoteModel.from_psb` 读取）：

- 每次 `collect()` 跑两遍，第二遍把 `_root` 置空（复用缓存全失效）强制全量重算；
- 逐部件深比较：tex/icon/label/z/opa/vis/grid_n/x/y、rect、矩阵、**全部网格点**
  （精确相等）、clip 数量与每个 clip 的网格/label；
- 不一致时 `printerr("REUSE MISMATCH: ...")` 并计入 `stat_verify_mismatch`。

这条门禁抓到过 3 个真实缺陷（clip 混用、registry 缺失、gid 撞车），
**任何渲染缓存改动都必须过这一关**。注意它会让 collect 跑两遍，性能数字不可用。

## 5. 下一步（按性价比排序）

### A. 把网格变形搬到 GPU（架构级正解，推荐）

原版 E-mote 就是 GPU 变形。我们现在的做法是：CPU 算 (WARP_SEG+1)²=36 个点 →
喂给 `Polygon2D`。改成：**传 warp 控制点给顶点着色器**，由 shader 做贝塞尔
变形，CPU 只更新控制点（每个部件 32 个 float，一次 uniform/纹理上传）。

- 收益：网格计算（占 collect 29%）几乎归零，且与部件数无关。
- 成本：自定义 `ShaderMaterial` + 网格拓扑固定化；需要处理 `Polygon2D`
  不支持自定义顶点属性的问题（改用 `MeshInstance2D` + `ArrayMesh`）。
- 风险：中。视觉上应与现在逐点计算一致（同一贝塞尔公式）。

**同一轮该做的事：mask 也搬到 GPU。** `docs/emote-driver.md` §4（2026-10-30
emotedriver.dll 逆向）定性：本作这一代是 TYPE1 纹理内嵌型，mask 为 **α 值
掩码**，原版走**离屏渲染目标**（`SetRenderTarget` + 视口设置）合成，并不在
CPU 上逐像素算。而我们的 `_bake_masked_texture` 是 GDScript 逐像素循环
（图标级分辨率，每个像素做贝塞尔反查 + α 合成），实测 `mask_bakes` 38 次 /
35 次渲染——命中率高所以不显眼，但它和网格计算是同一类浪费。
Godot 侧等价做法：`CanvasGroup` + `clip_children`，或给遮罩部件一个采样
mask 纹理的 shader，让 GPU 做 α 相乘。

### B. 降低网格分辨率（画质换性能，最快见效）

`WARP_SEG` 5 → 3：点数 36 → 16（-56%），网格计算约 -55%。
变形精度下降（每部件 4×4 四边形而非 6×6）。需要目视验收关键姿势。

### C. 打通子树回放（收益最大，但要先解决 stencil 语义）

若 A 落地，网格不再是瓶颈，子树回放的价值下降；若 A 不做，则需要：
把 clip 解析改成**不依赖遍历副作用**的形式——例如先把整棵树的 stencil 源
几何**一次性静态收集**（与变量无关的那部分），或在回放时按缓存的
"label → geom 列表"完整重建 registry（而不是依赖 `_register` 的祖先匹配）。
本文档 §3.2 已列出五种失败的尝试，接着做时从"registry 语义"入手，不要从
缓存键入手。

### D. stage 侧（20–44 ms/次）

`_render_slot` 的节点更新与 `_plan_parts` 字符串拼接。可改为整数结构键 +
常驻节点池，预计 -10 ms。收益有限，优先级最低。

### E. 顺带记录：bm 混合模式未接入（正确性，非性能）

同一份 `docs/emote-driver.md` §3 把 `bm` 全链钉死了：6 条
(BLENDOP, SRCBLEND, DESTBLEND) 三元组，样本里 **796 例 bm=3 = 乘算系**、
2 例 bm=4 = 屏幕系。播放器目前只透传 `bm`、不参与混合，所以腮红/阴影类
部件在视觉上是错的（不是性能问题，但同样待排期）。Godot 侧需要按三元组
写 shader 或材质混合，不能只靠默认 α 混合近似。

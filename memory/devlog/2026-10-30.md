# 2026-10-30

## 用户实测反馈三连（公网 Web 版）：CV 无声 / 火焰音效不停 / 立绘卡顿

排查手段：本地无 Godot，先装 Godot 4.7.2（`/f/codx/_godot/`），再用
Playwright+本机 Edge 驱动公网站点抓 `window.__animAudio` 与网络 Range 请求；
桌面端用 `--webpkg <r2 url>` 跑同一份线上包做逻辑复现（探针走文件日志，
**注意 Godot 的 stdout 在管道里全缓冲，进程被 kill 时输出全丢**——改用
`printerr` 或直接写文件）。

### 1. 火焰/环境音不结束（根因：0x89 完全没实现）

- 全量解析 sce（50,561 条记录）：**0x88 = 965 次**，通道分布
  9:421 / 10:327 / 1:78 / 2:54 / 6:48 / 11:24 / 12:13；**0x89 = 525 次**
  （单操作数 = 通道号，通道 9:249 / 10:203 / 6:47 / 11:16 / 12:8 / 1:1 / 2:1）。
- 旧实现把 0x88 压成单一 `AudioStreamPlayer`（后到顶先到），0x89 无 handler
  → 剧本停掉的环境床继续循环，即用户听到的"火焰停不下来"。
- 修复：AudioDirector 按通道号建播放器（按需创建、统一 Voice 总线、
  每通道独立 supersede token）；VM 发 `bgv_play{ch,name}` / `bgv_stop{ch}`；
  VOLUME 的 bgv 增益与台词 ducking 作用于全部通道；`_new_vm` 走 `stop_all_bgv`。
  验证：桌面 180s autoplay `bgv_play:1 / bgv_stop:1`（开场 ch6 床起停配对），0 错误。

### 2. 台词 CV 无声（根因：预取盲区 + 预取风暴 + 顶句丢弃）

- 探针实测：开场前 ~44s 无任何语音流（`voice_has_stream=false`）；桌面日志显示
  **首个语音行在 t≈48s**，而 `prefetch scene 0/1` 直到 **t≈144s** 才触发——
  scenes.json 的 `_SYSLABEL_` 标记在开场旁白段之后，之前的行完全没预取。
- 第二个原因：`_prefetch_scene` 一次性并发拉整段语音（scene 1 = 68 条），
  把"当前这一句"的按需取回挤在后面；播放层 `token != _voice_req` 即丢弃
  （慢网下每句必丢）。
- 修复：`_load_scenes_pf` 后立即 `_prefetch_scene(0)+(1)`；语音条目按剧本
  首用顺序**串行**预取（图片/bgm 同样串行，避免抢占带宽）。
- 未解：顶句丢弃策略本身保留（用户已翻页时播旧句是错的），依赖预取把
  取回提前到显示之前。

### 3. 立绘卡顿（collect() 热路径）

- 线上 wasm 实测（旧构建）：293ms/次渲染、collect 占 79%、`grid_calls` 6370/13 次渲染。
- 三项纯缓存（结果不变）：
  - 帧求值记忆化：key=(layer 节点, 动作时间 t)，存在 layer 节点上（`_fmemo`，上限 24），
    眨眼/口型档位变化时只有 t 真的变了的层重算；
  - warp / affine 记忆化挂在被记忆化的 frame dict 上；
  - `chain_plan()`：把 warp 之间的纯仿射层预合成，单点变换 O(#warps) 而非 O(depth)。
- 网格缓存键由字符串拼接改为 `PackedInt64Array`（**坑：`_grid_lru` 原本是
  `Array[String]` 类型化数组，塞整数键会每次触发运行时错误，性能反而劣化 2.6×**）。
- 新自检 `player/tests/test_chain_compose.gd`：4000 条随机链（0–2 warp）
  与逐点循环对比，最坏误差 **0.0**（**坑：Godot 标准构建的 `Vector2` 是 32 位浮点，
  中间量必须用裸 float 标量，否则 warp 输入被截断到 float32**）。
- 驱动合并上限：过渡中 0.15s、静止/口型 0.45s。
- 桌面 A/B（同一线上包、180s autoplay、事件流逐项一致 149/148/effects 全同）：
  render_ms 53.0s→26.8s、renders 316→272、单次 168ms→98ms、
  collect 47.9s→23.2s、grid 30.9s→12.7s。300s 段落（过渡密集）同样口径 -12%。

## 立绘渲染性能追查（同日晚，用户质疑「一个立绘不可能要渲染以秒计」）

- 结论性文档：`docs/render-perf-analysis.md`（实测数据 / 已落地优化 / 两条失败路线的完整结论 / 下一步）。
- 基线实测（桌面 headless + 线上包，180s）：**每次渲染访问 546 个层节点、产出仅 55 个部件**，
  单次 143.8ms、每层摊销 225µs。wasm 侧 293ms。即"每次眨眼/口型都从根全量重算"是架构问题，不是常数因子。
- 已落地（commit fae856a）：帧求值记忆化、warp/affine 记忆化、`chain_plan` 仿射预合成、
  驱动合并 0.30→0.45s。168ms → 98ms（同段事件流逐项一致）。
- **两条失败路线（已回退，勿重走）**：
  1. Ctx 上下文复用：复用率 79% 但单次渲染无改善（省下的只是 Ctx 构建）；
     且双路深比较抓到 clip 混用（86/88）。加 `clip_key`（stencil label 集合 hash）
     后 0 不一致但复用率塌到 ~0、仍 146ms。
  2. 子树部件列表回放 + 变量依赖位图：**单次渲染 7.2ms（20 倍）**，但 clip 不一致
     135/138（label `トリミング枠`，registry 为空）。五种修法全部无效（reg_geoms 重放、
     `_resolve_clips` 幂等、gid→对象身份、has_stencil 子树标志、二分）。二分证明问题在
     "复用 × stencil"，不在回放本身。
- 根因判断：`part.clip` 依赖"本轮 Inst 的 registry"，而 registry 是遍历的副作用；
  `_register` 只向**祖先 label** 注册，而 stencil 可引用**同 Inst 内任意 label**——两者不等价。
- 新增可复用门禁：`ANIM_VERIFY=1` → collect 双跑（第二遍清空复用缓存）逐部件深比较
  （含全部网格点与 clip 几何），不一致即 printerr。它抓到过 3 个真实缺陷，
  **任何渲染缓存改动必须过这一关**（注意会跑两遍，性能数字不可用）。
- 下一步建议（文档 §5）：A 把变形搬到 GPU（原版做法，收益与部件数无关，推荐）；
  B `WARP_SEG` 5→3（画质换性能，-55% 网格计算）；C 打通子树回放（须先解决 registry 语义）；
  D stage 侧节点更新（-10ms，优先级最低）。
